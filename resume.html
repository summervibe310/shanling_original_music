第一部分：项目背景与架构概览

这个CRM是为二手工业设备交易平台（51panhuo.com）从零搭建的内部系统，用户是50-100名销售和运营人员。核心场景是销售从拿到线索开始，跟进客户、匹配设备、报价、收订金到成交的全流程管理。

系统采用经典的三栏布局：左侧功能菜单、中间数据列表、右侧详情/操作面板。用户可以在中栏和右栏同时打开多个Tab页面，类似于浏览器的多标签页体验。这个交互模式是整个系统架构的核心，也是最大的技术挑战。

技术选型理由

  • Vue 3：Composition API更适合大型项目，逻辑按功能组织而不是按选项类型分散；公司对IE没有兼容要求
  • Vite：开发服务器冷启动2-3秒，热更新毫秒级，比之前Webpack项目15秒+提升明显
  • Pinia：相比Vuex，去掉了mutations，TypeScript支持开箱即用，API更简洁
  • Element Plus：表单密集型后台管理的首选，模板语法开发效率高

第二部分：多Tab缓存架构（核心设计）

这是整个系统技术含量最高的部分。用户在中栏打开客户列表，点击某个客户后在右栏打开客户详情；切换到另一个客户时，右栏可以覆盖上一个Tab，也可以锁定后同时打开多个进行对比。

方法 功能 技术细节

配合Vue的<KeepAlive>组件，切换Tab时组件实例被缓存，表单填写状态、滚动位置、筛选条件都不会丢失。这是B端高频操作场景下最重要的体验优化。

第三部分：9阶段意向状态机

二手设备交易流程很长，从销售第一次接触客户到最终成交，中间要经历多个阶段。我把这个流程抽象为9个状态：

阶段状态说明
1初挖销售初步接触客户，了解基本需求
2深挖深入了解客户预算、设备类型偏好、时间节点
3配货根据需求在设备库中匹配合适的二手设备
4报价向客户提交正式报价
5议价价格谈判阶段
6订金客户支付订金，锁定设备
7成交完成交易
8关闭意向终止（丢单或客户放弃）
9复购老客户再次购买

关键设计：报价不是独立模块，而是通过创建特殊类型的跟进记录（type='50'）来实现。这样做的好处是：所有报价操作天然进入跟进时间轴，无需额外开发审计日志功能。每条报价记录都可以追溯到哪个销售、什么时间、报了哪个设备、什么价格，实现了全流程审计可追溯。

第四部分：4K等级自动判定引擎

销售需要根据客户信息的完整度来判断客户质量。我设计了9项必填项的检查规则，自动驱动客户等级升降：

  • 客户名称、联系电话、设备类型需求、预算范围、采购时间节点、决策人角色、公司名称、使用地点、历史购买记录
  • 9项全部满足 → A级（高意向）
  • 满足6-8项 → B级
  • 满足3-5项 → C级
  • 满足0-2项 → D级

等级判定在前端实时计算，任何必填项的变更都会触发重新判定。规则配置化，后续增加或调整判定条件只需修改配置对象，不需要改动组件逻辑。

第五部分：AXB隐私号安全方案

二手设备交易平台的核心资产是设备信息和客户关系。为了防止销售拿到客户真实手机号后私下交易（飞单），集成了阿里云AXB隐私号服务。

  • 销售点击"联系卖家"按钮 → 系统向阿里云申请临时中间号 → 销售拨打中间号 → 阿里云转接到卖家真实号码
  • 通话页面显示倒计时，控制通话时长
  • 通话结束后强制弹出"机况记录"表单，要求销售填写通话内容摘要
  • 所有通话记录留痕，包含主叫方、被叫方、通话时间、机况记录

第四部分：事件驱动异步同步机制

这是整个模块的核心设计决策。货主注册、运单签收这些操作有自己的主事务，如果在业务方法里直接调用翔和翎HTTP接口，对方超时会把主事务也拖长，甚至阻塞数据库连接池。

我的方案是三层解耦：

  1. 业务层发布事件：业务方法完成后通过Spring Event发布领域事件（如CreateOwnerEvent）
  2. 事务提交后触发监听：@TransactionalEventListener(AFTER_COMMIT)保证本地数据库事务提交后才执行监听器
  3. 异步执行HTTP调用：@Async用独立线程池发送HTTP请求到翔和翎，主业务线程立即返回，不受三方接口响应时间影响
为什么不是AFTER_COMPLET而不是AFTER_COMMIT？AFTER_COMPLET在事务回滚后也会执行，会导致没存上的数据反而同步到翔和翎。AFTER_COMMIT只在事务成功提交后触发，保证数据一致性。

第五部分：MD5签名鉴权与回调

出站签名（AppSignUtil.getSign）：

  • 把请求参数按key排序拼接
  • 加上apiKey作为盐值
  • MD5加密生成签名
  • 请求时带timestamp和sign两个字段

入站回调验签（verifySign）：

  • 先校验timestamp在1分钟有效期内，防止重放攻击
  • 重新计算签名和传来的sign比对
  • 不匹配就抛InvalidAccessException

第六部分：人车合照审核闭环

这是我最完整的业务闭环实践。翔和翎要求司机上传车辆正面人车合照后同步到他们平台审核，审完再回调我们更新审核状态。我负责了整条链路：

  1. 数据库字段扩展：在car_license_audit表新增人车合照审核字段（审核状态、审核意见）
  2. 事件触发：CarLicenseAuditServiceImpl审核完成后发布CreateDriverTruckEvent或UpdateDriverTruckEvent
  3. 异步同步：XhlEventListener异步调用XhlApiClient的createDriverTruck或updateDriverTruck，POST到翔和翎
  4. 回调落库：XhlCallBackApiServiceImpl接收对方回调，更新car_license_audit的合照审核字段，区分前车牌照和后车牌照做字段映射

第七部分：联调踩坑记录

踩坑1：运单接口URL混用

联调运单状态同步时，对方反馈修改和删除运单没生效。查日志发现HTTP有返回但对方数据没变。回头对照ApiAccessTest里的Demo URL，发现XhlApiClient里复制粘贴时URL没改对：删除运单的方法里写成了waybill/update，修改运单的方法里写成了order/send。修正后四个接口全部通过。后来我把所有URL提取成常量，避免再犯。

踩坑2：文档与实网行为不一致

对接过程中多次遇到翔和翎文档写的参数名、返回值格式和实际接口行为不一致的问题。我养成了先写ApiAccessTest验证接口实际行为的习惯，遇到不一致就截图留证跟对方技术支持对齐，避免在业务代码里反复改参数名。

第八部分：技术反思与改进方向

  • 异步失败重试机制：当前异步推送失败只打日志，后续可以加失败记录表和定时任务重试，重试三次后告警
  • 回调幂等性加固：目前靠更新同一条记录保证业务幂等，数据库层面可以加唯一约束防并发写入
  • 出站客户端抽象：32个API的参数组装逻辑可以进一步模板化，减少重复代码
